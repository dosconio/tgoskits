## 三、分步路线规划

核心原则：**先让 OVMF 跑起来，再慢慢实现复杂功能。每个阶段只做最小必要的工作，不追求完美。**

### Step 5: 打通从 OVMF 到 Linux 内核启动的完整链路 🔴🟡

这是当前最关键的阶段，目标是：**修复 CPUID 死循环 → OVMF 完成初始化 → 通过 fw_cfg 直接加载 Linux 内核并启动**。

> **策略选择：fw_cfg 路径 A** — 通过 fw_cfg 将 kernel + initrd + cmdline 直接传递给 OVMF 的 QemuLoadKernelImage 驱动。绕过 virtio-blk VirtQueue I/O 的复杂实现，用最短路径验证 "OVMF → Linux" 的端到端可行性。

---

#### 5a. 修复 CPUID leaf=0x1 子叶死循环（阻塞性修复）

**问题位置：** [handle_cpuid()](file:///home/phina/Documents/tgoskits/components/x86_vcpu/src/vmx/vcpu.rs#L1380-L1505)

**具体问题：** `leaf=0x1` 的处理只调用 `cpuid!(1, rcx)` 透传 host CPU 结果。OVMF 首先查询 `leaf=0x1, sub=0x0` 得到非零 EAX，然后继续查询 `sub=0x2, 0x4, 0x38...` 期望 sub>0 返回全零 EAX（表示无效子叶）。但当前代码对 sub>0 返回与 sub=0 相同的结果，导致 OVMF 无限遍历。

**修复方案（最小改动）：**

```rust
// handle_cpuid() 中 leaf=0x1 分支，在调用 cpuid 前检查 subleaf：
if regs.rcx >= 4 {
    // subleaf >= 4：返回全零（根据 Intel SDM，leaf 0x1 有效子叶为 0-3）
    regs.rax = 0;
    regs.rbx = 0;
    regs.rcx = 0;
    regs.rdx = 0;
} else {
    cpuid!(1, rcx);
}
```

**验证点：**
- OVMF 不再在 `0x82dbb8-0x82dbc5` 之间无限循环
- CPUID VM-Exit 后续出现新的 VM-Exit 类型（IOAPIC MMIO 访问）
- 看到 `handle_mmio_read` / `handle_mmio_write` 被调用（IOAPIC 区域 `0xFEC00000`）

---

#### 5b. 验证 IOAPIC MMIO + 中断注入链路（伴随 CPUID 修复自动推进）

CPU ID 修复后，OVMF 自然会推进到 IOAPIC 初始化阶段。Stage 4 的代码已经完备，此处主要验证端到端行为。

**预期 OVMF 行为：**
1. 读取 IOAPIC ID (index 0x00) 和 IOAPICVER (index 0x01) → 应返回 `0x00170011`
2. 初始化所有 24 个 RTE → 一系列 IOREGSEL + IOWIN 写入
3. 通过 MADT 表确认 IOAPIC GSI 映射

**验证点：**
- 日志中出现 `[IOAPIC] write IOREGSEL:` 和 `[IOAPIC] read reg`
- 日志中出现 `[IOAPIC] write reg[X] = ...` (RTE 配置)
- 无异常的 EPT_VIOLATION、无 unsupported VM-Exit

**常见问题排查：**
- RTE lo/hi 位掩码是否正确（bit 12 必须写 0，hi 仅保留 bits 31:24）
- EPT_VIOLATION→IOAPIC MMIO 转发中 RIP 推进逻辑
- MMIO 访问宽度是否为 32-bit

---

#### 5c. 通过 fw_cfg 传递 kernel + initrd 启动 Linux（核心新功能）

**为什么不走 VirtQueue I/O：** 实现完整 VirtQueue I/O + 磁盘镜像加载需要 300-500 行新代码，且需处理分区表、文件系统等复杂问题。fw_cfg 路径已经工作正常（Stage 2 验证通过），可以直接利用现有基础设施。

**实现思路：**

OVMF 内建的 `QemuLoadKernelImage` 驱动（如果 OVMF 编译时包含了此功能）会在启动时检查 fw_cfg 中的特定文件项。如果找到 kernel 镜像，就跳过磁盘枚举，直接通过 fw_cfg 读取并启动。

**要做的修改：**

**A. 扩展 TOML 配置（`axvmconfig` + VM 配置文件）：**

在 `VMKernelConfig` 中新增三个字段：
```rust
// 新增字段 — fw_cfg 直接内核加载
kernel_cmdline: Option<String>,   // 内核命令行参数
initrd_path: Option<String>,      // initramfs 文件路径
initrd_load_gpa: Option<usize>,   // initrd 在 guest 内存中的加载地址
```

示例 TOML 配置：
```toml
boot_mode = "uefi"

# fw_cfg 内核直接启动
kernel_cmdline = "console=ttyS0 earlyprintk=serial root=/dev/ram0 ro"
initrd_path = "/guest/initrd.img"
initrd_load_gpa = 0x4000000

[kernel]
kernel_path = "/guest/bzImage"        # ← 这个已有
kernel_load_addr = 0x10000000
# ... 其他已有字段 ...
```

**B. 扩展 fw_cfg 文件注册（`os/axvisor/src/vmm/images/mod.rs`）：**

在 `setup_fw_cfg_and_acpi()` 中，注册 fw_cfg 内核启动文件项：

```rust
// 1. 注册内核镜像（kernel_path 指向的文件）
//    fw_cfg 文件名为 "opt/org.qemu/kernel" — QEMU/OVMF 标准键名
let kernel_data = /* 从 rootfs 读取 kernel_path 指向的文件 */;
fw_cfg.add_file("opt/org.qemu/kernel", &kernel_data);

// 2. 注册内核命令行
if let Some(cmdline) = &config.kernel_cmdline {
    fw_cfg.add_file("opt/org.qemu/cmdline", cmdline.as_bytes());
}

// 3. 注册 initrd（从 rootfs 读取，写入 guest 内存，同时注册到 fw_cfg）
if let Some(initrd_path) = &config.initrd_path {
    let initrd_data = /* 从 rootfs 读取 initrd 文件 */;
    // 写入 guest 内存（在 initrd_load_gpa 处）
    // ...
    fw_cfg.add_file("opt/org.qemu/initrd", &initrd_data);
}

// 4. 设置 bootorder，将 fw_cfg 直接启动作为最高优先级
//    HALT 表示直接 fw_cfg 启动，不尝试从其他设备引导
fw_cfg.add_file(
    "etc/bootorder",
    b"\x04\x00\x00\x00" // fw_cfg boot entry type
);
```

**C. 文件读取基础设施（可能已存在，需确认）：**

当前 `load_vm_images_uefi()` 已经能从 rootfs 读取 pflash 文件（通过 `read_file` 或类似的 API）。需要确认同样的机制是否可用于读取 kernel 和 initrd 文件。如果 rootfs 文件读取 API 已就绪，直接复用即可。

**验证点：**
- 日志中出现 `Added fw_cfg file: opt/org.qemu/kernel` 等
- OVMF 不再进入 "BdsDxe: failed to load Boot0001..." 的失败路径
- OVMF 输出 `QemuLoadKernelImage: ...` 或类似日志（如果 OVMF 包含此驱动）
- 最终看到 Linux 内核启动日志（如 `Linux version ...`、`Booting the kernel` 等）

**如果 OVMF 不包含 QemuLoadKernelImage 驱动（Plan B）：**

如果当前使用的 OVMF_CODE.fd 没有编译 QemuLoadKernelImage，有两条备选路径：
1. **换一个包含此驱动的 OVMF 版本** — QEMU 发行包中的 OVMF 通常包含此功能
2. **退回到 VirtQueue I/O + 磁盘镜像** — 实现最小 VirtQueue I/O（解析 descriptor chain + 返回磁盘镜像数据），此方案留待 Step 5 路径 A 不通时再实施

### Step 6: i8259 PIC 模拟（可选，按需实现）

**依赖：** Step 5

**为什么可能不需要：** OVMF 在 DXE 阶段已切换到 APIC 模式。但如果 OVMF 在 SEC/PEI 阶段访问 i8259 端口 (0x20/0x21, 0xA0/0xA1)，当前 `intercept_all()` 策略会拦截这些访问并返回 "device not found"，可能导致 OVMF 异常。

**最小实现：**
- 在 axvisor 中 inline 实现 PIC 主片和从片的 ICW1-ICW4 初始化序列
- OCW1 (IMR) 读写：默认屏蔽所有中断
- OCW2 (EOI) 写入：忽略
- 不需要实际中断路由（OVMF 不使用 PIC 中断）

**判断是否需要：** Step 5 运行后观察日志，如果有 `device not found for port 0x20/0x21` 且后续行为异常，则实现此步骤。

### Step 7: SMP 多 vCPU 启动 (INIT/SIPI)

**优先级：** 中等。先单 vCPU 跑通 Linux 再考虑 SMP。

### Step 8: vLAPIC EOI 广播 → vIOAPIC

**依赖：** Step 5

**要做什么：**
1. vLAPIC EOI 写入时通知 vIOAPIC：`GLOBAL_VIOAPIC.get().unwrap().eoi(vector)`
2. vIOAPIC eoi() 中清除 Remote IRR，重新评估 Level 触发中断状态

**为什么重要：** Level 触发中断在 EOI 后需要 IOAPIC 重新拉低中断线。无 EOI 广播则 Level 中断只能触发一次。

## 五、关键风险与缓解措施

| 风险 | 可能性 | 影响 | 缓解 |
|------|--------|------|------|
| CPUID 修复后 OVMF 仍有其他死循环 | 中 | 高 | 加 VM-Exit 计数器，检测长时间无 IO/MMIO VM-Exit 的异常状态 |
| IOAPIC MMIO 转发存在边界情况 | 中 | 中 | IOREGSEL/IOWIN 间接访问已实现，主要风险在访问宽度不是 32-bit |
| OVMF 不含 QemuLoadKernelImage 驱动 | 中 | 高 | Plan B：换 OVMF 版本或退回到 VirtQueue I/O + 磁盘镜像 |
| fw_cfg 文件项命名不符合 OVMF 预期 | 低 | 中 | 参照 QEMU 源码确认键名（`opt/org.qemu/kernel` 等），必要时加调试日志列出所有注册的 fw_cfg 文件 |
| Guest 内存不足（32 MiB 不够 kernel + initrd） | 中 | 高 | 增加 memory_regions 到 256 MiB 或更大 |
| OVMF 检测到 i8259 缺失而异常 | 低 | 中 | 观察 Step 5 日志，按需在 Step 6 实现最小 PIC stub |
| Linux 内核启动后因缺少 virtio 设备驱动 panic | 中 | 中 | kernel cmdline 设置正确的 console，使用 initramfs 包含必要驱动 |

### 唯一核心目标

在 **Step 5** 中一次性打通从 OVMF 到 Linux 内核启动的完整链路：

```
修复 CPUID (5a) → IOAPIC 初始化验证 (5b) → fw_cfg 传递 kernel/initrd/cmdline (5c) → Linux 启动
```

### 策略选择

- **主路径：fw_cfg 直接内核加载** — 利用已有的 fw_cfg 基础设施，绕过 VirtQueue I/O 和磁盘镜像的复杂性
- **Plan B：** 如果 OVMF 不含 QemuLoadKernelImage，换 OVMF 版本或实现最小 VirtQueue I/O

### 一句话建议

> **集中精力在 Step 5 — 一个阶段完成从 CPUID 修复到 Linux 内核启动的全链路。不要分散注意力到外围功能。**
