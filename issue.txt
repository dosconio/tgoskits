## 修复记录：内存分配失败 (256 MiB)

### 根本原因

TLSF 字节分配器不适合分配 VM 大块内存（256 MiB），原因有三层：

1. **TLSF 分级列表向上取整**：TLSF 的 `map_ceil_and_unmap` 会将搜索大小向上取整到分级边界，导致精确大小的内存池无法满足分配请求。例如请求 1.5 MiB，TLSF 可能需要更大的连续空闲块。
2. **元数据开销**：每个 TLSF 池需要 block header（GRANULARITY/2 = 16 字节）+ sentinel block（GRANULARITY = 32 字节），加上对齐填充。之前的堆扩展逻辑未考虑这些开销，导致添加的池可用空间不足。
3. **VM 内存不应经过 TLSF**：256 MiB 的 VM 内存区域通过全局分配器（TLSF）分配，会消耗大量 TLSF 堆空间，导致后续小分配（如 OVMF 镜像读取的 Vec 缓冲区）也因内存不足而失败。

### 修复思路

**核心策略**：VM 内存区域绕过 TLSF，直接使用 page allocator 分配。

1. 在 `axvm` 添加 `register_memory_region` API，接受外部已分配的内存指针
2. 在 `axvisor` 的 `vm_alloc_memorys` 中使用 `alloc_pages` 直接分配 VM 内存
3. 改进 `ax-alloc` 堆扩展逻辑，补偿 TLSF 元数据开销并使用 power-of-two 取整
4. 增加 QEMU 主机内存到 1 GiB，为 hypervisor + VM 提供足够空间

### 修改文件

| 文件 | 修改内容 |
|------|----------|
| `components/axvm/src/vm.rs` | 新增 `unsafe fn register_memory_region()`，接受外部已分配的内存指针，`needs_dealloc=false` 时由调用方管理释放。`cleanup_resources` 已正确跳过此类区域 |
| `os/axvisor/src/vmm/config.rs` | `vm_alloc_memorys` 中 `MapAlloc`/`MapIdentical` 改用 `global_allocator().alloc_pages()` 直接分配页面，再通过 `register_memory_region` 注册到 VM |
| `os/arceos/modules/axalloc/src/default_impl.rs` | 堆扩展逻辑：增加 `BYTE_ALLOC_OVERHEAD = PAGE_SIZE` 补偿 TLSF 元数据开销；统一使用 `next_power_of_two` 取整（TLSF 分级结构要求）；使用 layout 对齐分配页面；分配失败时二分回退 |
| `os/axvisor/configs/qemu/qemu-x86_64.toml` | QEMU 内存 512M → 1G |
| `platform/x86-qemu-q35/axconfig.toml` | 物理内存 0x2000_0000 → 0x4000_0000 |

### 验证结果

- 256 MiB VM 内存通过 page allocator 直接分配成功
- OVMF 镜像加载成功（pflash0 + pflash1）
- VM 成功启动运行，vLAPIC timer 周期性触发
- clippy 和 fmt 检查通过

## 修复记录：PIT 基于真实时间推进

### 根本原因

i8254 PIT 模拟原来使用访问计数驱动时间推进（`ACCESSES_PER_DECREMENT=16`），即每 16 次 I/O 端口访问才推进计数器一次。OVMF 在 DXE 阶段使用 8254TimerDxe 驱动配置 PIT Counter 0 为 Mode 2 (Rate Generator)，但 OVMF 配置完 PIT 后不再频繁访问端口，导致 IRQ0 永远不会触发，OVMF 卡在等待定时器中断的循环中。

### 修复思路

1. **改为基于真实时间推进**：使用 `axvisor_api::time::{current_ticks, ticks_to_nanos}` 获取平台时间，计算经过的真实时间并转换为 PIT ticks
2. **添加 `advance_to_now()` 公共方法**：在每次 VM entry 前调用，确保计数器与真实时间同步
3. **添加 `GLOBAL_PIT` 全局单例**：`spin::Once<Arc<I8254Pit>>`，在 VM 创建时注册，vCPU 运行循环中通过它调用 `advance_to_now()`
4. **支持 Mode 2 IRQ0 脉冲**：在 `advance_by_ticks()` 中为 Mode 2 添加周期边界检测，在重载边界产生 IRQ0 脉冲
5. **添加 `counter0_deassert_irq()`**：用于 Guest 处理中断后取消 IRQ0 断言

### 修改文件

| 文件 | 修改内容 |
|------|----------|
| `components/i8254_pit/src/lib.rs` | 重写时间推进机制：`access_count` → `last_advance_ns`；添加 `GLOBAL_PIT` 全局单例；添加 `advance_to_now()` 公共方法；添加 `PitCounter::advance_by_ticks()` 支持 Mode 0/2/3 批量推进；删除 `tick()` 方法；添加 `counter0_deassert_irq()`；实现 `Send+Sync` |
| `components/i8254_pit/Cargo.toml` | 添加 `axvisor_api` 和 `spin` 依赖 |
| `os/axvisor/src/vmm/vcpus.rs` | 在 vCPU 运行循环的 `check_events()` 后添加 `GLOBAL_PIT.advance_to_now()` 调用 |
| `os/axvisor/src/vmm/images/mod.rs` | 将 PIT Arc 注册到 `GLOBAL_PIT.call_once()`，同时作为端口设备添加 |

## 修复记录：CCR 周期定时器回绕计算

### 根本原因

vLAPIC `read_ccr()` 在周期定时器到期后返回 0，而非按 Intel SDM 规定回绕重新计算当前计数值。周期模式下 CCR 应该从 ICR 重新开始倒计数，读取时返回当前周期内剩余的计数值。

### 修复思路

在 `read_ccr()` 中，当 `current_ticks >= deadline_ticks` 时：
- **周期模式**：计算从 `last_start_ticks` 开始经过的总 ticks，取模得到当前周期内剩余 ticks，转换为 CCR
- **单次模式**：保持返回 0（定时器已停止）

### 修改文件

| 文件 | 修改内容 |
|------|----------|
| `components/x86_vlapic/src/timer.rs` | `read_ccr()` 添加周期模式回绕计算：`remaining = period_ticks - (elapsed % period_ticks)` |

## 修复记录：pflash0 EPT 写权限缺失导致 OVMF SEC 阶段 LZMA 解码死循环

### 根本原因

OVMF_CODE.fd 所在的 pflash0 区域 (GPA 0xFFC00000-0xFFFFFFFF) 的 EPT 权限被配置为 `0x5` (R|X)，缺少写权限。OVMF SEC 阶段需要解压固件卷 (FV)，LZMA 解码器将解压后的数据写回 pflash0 区域内的地址。写入操作触发 EPT violation，但当前 EPT violation 处理逻辑中：

1. pflash0 不在 APIC/IOAPIC/PCI MMIO 范围内
2. pflash0 的原始映射标志不包含 WRITE，`handle_page_fault` 返回 false
3. 结果是 EPT violation UNHANDLED，没有注入 #PF 到 guest
4. Guest 的写入被静默丢弃，LZMA 解码器的内存复制循环 (`mov [ecx-1], bl; cmp dx, cx; jne`) 永远无法完成

### 修复思路

将 pflash0 区域的 EPT 权限从 `0x5` (R|X) 改为 `0x7` (R|W|X)。OVMF SEC 阶段需要写入 pflash0 区域来解压固件卷，这是正常行为。QEMU 的 pflash 模型也允许 guest 写入 pflash 区域的 RAM 映射。

### 修改文件

| 文件 | 修改内容 |
|------|----------|
| `os/axvisor/vms/uefi-x86_64-qemu.toml` | pflash0 区域权限从 `0x5` (R|X) 改为 `0x7` (R|W|X) |

### 验证结果

- OVMF 成功通过 SEC 阶段（LZMA 解压不再死循环）
- OVMF 进入 PEI/DXE 阶段，读取 fw_cfg 设备
- OVMF 访问 PCI 设备（Host Bridge, LPC Bridge）
- OVMF 输出串口字符
- 但 OVMF 仍在 32 位保护模式中循环（新问题，见下方）

## 修复记录：PIT/PIC/APIC_BASE/INTERRUPT_WINDOW 四个关键 bug (2026-06-17)

### 根本原因

OVMF 在 DXE 阶段卡在 32 位保护模式的 spin loop 中，无法进入长模式。根因是中断传递路径完全断裂，OVMF 等待的定时器事件永远无法到达。通过全面分析发现 4 个关键 bug：

1. **Bug 1: PIT irq0_asserted 永不清除** — `i8254_pit` 的 `advance_to_now()` 中，`irq0_asserted` 一旦设为 true 就永不清除，导致 PIT 只能触发一次 IRQ0 上升沿，所有后续周期都被静默丢弃。OVMF 永远收不到第二个定时器中断。

2. **Bug 4: 8259 PIC 初始状态为 Idle** — `i8259_pic` 的 `PicChip::new()` 初始化 `state=Idle, imr=0xFF`，导致 `pending_irq()` 在 `state != Ready` 时返回 None。OVMF 早期启动阶段（在执行 ICW 初始化序列前）需要通过 8259 PIC 接收 IRQ0，但 PIC 处于未初始化状态，所有中断被丢弃。

3. **Bug 5: APIC_BASE MSR 写入被忽略** — `handle_apic_base_msr()` 的 write 路径只记录日志但不更新 vLAPIC 的 `apic_base` 状态。OVMF 写入 APIC_BASE MSR 后，vLAPIC 的 `is_software_enabled()` / `is_x2apic_enabled()` 仍返回旧值，导致中断注入逻辑走错分支。读取路径返回硬编码值 `0xFEE0_0900`（x2APIC enabled），但 OVMF 期望读取它之前写入的值。

4. **INTERRUPT_WINDOW VM-Exit 返回 None** — `builtin_vmexit_handler()` 中 INTERRUPT_WINDOW 处理器返回 `None`，导致 `inner_run()` 将其传递给外层 `run()` 的 match。`run()` 没有 INTERRUPT_WINDOW 分支，落入 `_ =>` 分支被当作 "unsupported VM-Exit"，vCPU 被 halt。这导致 OVMF 在第一次中断窗口 VM-exit 时就停止运行。

### 修复思路

1. **PIT 脉冲模式**：对于 Mode 2/3（周期模式），每个周期边界先 deassert 再 assert IRQ0，模拟真实 PIT 的脉冲行为。这样 PIC 能看到上升沿，持续产生周期性中断。

2. **PIC 固件就绪默认状态**：将 PIC 初始化为 "firmware-ready" Virtual Wire Mode 默认状态（state=Ready, base=0x08, imr=0xFB 仅允许 IRQ0）。这模拟真实硬件上 BIOS 已初始化 PIC 的状态。如果 guest 后续执行 ICW1-4 序列，会覆盖这些默认值。

3. **APIC_BASE MSR 状态同步**：
   - 在 `VirtualApicRegs` 添加 `set_apic_base()` 方法，实际更新 `apic_base` 字段
   - 在 `EmulatedLocalApic` 暴露 `apic_base()` 和 `set_apic_base()` 公开方法
   - `handle_apic_base_msr()` write 路径调用 `self.vlapic.set_apic_base(value)`
   - read 路径返回 vLAPIC 的实际 `apic_base()` 值
   - vLAPIC 初始化时设置上电默认值：`0xFEE0_0900 | (BSP << 8)`

4. **INTERRUPT_WINDOW 返回 Some(Ok(()))**：将 INTERRUPT_WINDOW 处理器的返回值从 `None` 改为 `Some(Ok(()))`，使其在 `builtin_vmexit_handler` 中完全处理，不传递到外层 `run()`。

### 修改文件

| 文件 | 修改内容 |
|------|----------|
| `components/i8254_pit/src/lib.rs` | `advance_to_now()` 中 PIT IRQ0 改为脉冲模式：每个周期边界先 deassert（falling edge）再 assert（rising edge），使 PIC 能持续看到上升沿。删除未使用的 `mode`/`reload`/`null_count` 局部变量 |
| `components/i8259_pic/src/lib.rs` | `PicChip::new()` 初始化为固件就绪默认状态：`state=Ready, base=0x08, imr=0xFB`（仅允许 IRQ0）。`PicState::Idle` 添加 `#[allow(dead_code)]` |
| `components/x86_vlapic/src/vlapic.rs` | 添加 `set_apic_base()` 方法；`apic_base()` 移除 `#[allow(dead_code)]`；初始化 `apic_base` 为上电默认值 `0xFEE0_0900 | (BSP << 8)` |
| `components/x86_vlapic/src/lib.rs` | `EmulatedLocalApic` 添加 `apic_base()` 和 `set_apic_base()` 公开方法 |
| `components/x86_vcpu/src/vmx/vcpu.rs` | `handle_apic_base_msr()` write 路径调用 `self.vlapic.set_apic_base(value)`；read 路径返回 vLAPIC 实际值；`INTERRUPT_WINDOW` 处理器返回值从 `None` 改为 `Some(Ok(()))` |

## 修复记录：fw_cfg DMA 地址构建 bug + PCI MMIO 窗口范围 + Guest RAM 扩展

### 根本原因

OVMF 的 fw_cfg DMA 缓冲区地址 0x48f88100 超出 257MB guest RAM 范围，导致 DMA 操作失败。问题有两层：

1. **fw_cfg DMA 地址构建 bug**：port 0x514/0x518 的 high/low 逻辑反了。OVMF 在 32 位保护模式下写入时，port 0x514 是 DMA 地址偏移 0（高 32 位），port 0x518 是偏移 4（低 32 位）。代码把 port 0x514 当作低 32 位、port 0x518 当作高 32 位，导致组合出的 GPA = 0x48f8810000000000（错误）而非 0x48f88100（正确）。

2. **PCI MMIO 窗口范围过大**：PCI MMIO 窗口硬编码为 0x40000000-0xFEC00000，而 QEMU Q35 的 PCI MMIO 窗口从 0xE0000000 开始。0x48f88100 落在 0x40000000-0xE0000000 范围内，被 EPT violation handler 误判为 PCI MMIO 访问，映射了 dummy_ff_page（全 0xFF 只读页），写操作被静默丢弃。OVMF 误以为该地址有可用内存，在此分配了 DMA 缓冲区。

3. **Guest RAM 不足**：即使修复了上述两个问题，0x48f88100 (~1.17GB) 仍超出 257MB RAM 范围。需要增加 guest RAM 到 2GB 以覆盖 OVMF 的 DMA 缓冲区地址。

### 修复思路

1. **交换 port 0x514/0x518 的 high/low 处理逻辑**：port 0x514 存储高 32 位，port 0x518 存储低 32 位并触发 DMA
2. **将 PCI MMIO 窗口起始从 0x40000000 改为 0xE0000000**：匹配 QEMU Q35 的实际 PCI MMIO 窗口范围
3. **将 guest RAM 从 256MB 增加到 2GB**：覆盖 OVMF 的 DMA 缓冲区地址和 TempRam 区域

### 修改文件

|------|----------|
| `components/fw_cfg/src/lib.rs` | 将 `dma_addr_low` 重命名为 `dma_addr_high`，交换 port 0x514/0x518 的处理逻辑：port 0x514 存储高 32 位，port 0x518 存储低 32 位并触发 DMA |
